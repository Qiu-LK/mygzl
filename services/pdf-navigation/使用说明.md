# 页码与按实际页数自动目录

这是独立的PDF渲染桥接服务。不会覆盖原有8080服务，也不改已有PDF预检/OCR服务。Dify不增加LLM；现有「请求体生成」Python代码保持不变。

## 已实现的规则

- 先渲染真实PDF，以此时总页数（包含封面，不含尚未添加的目录）判断。
- 少于30页：只加页码，不加目录。
- 30页及以上：封面后插入目录，使用真实PDF标题落页，插入后修正全部页码。
- 目录优先收录正文h2标题；其他结构没有h2时使用可用的最上层标题，不把每个h3函数都列进目录。
- 底部居中页码。封面计为PDF第1页但不显示数字，目录/正文显示的数字与阅读器页序一致。
- 目录条目可点击跳到真实正文页，PDF书签也按插入后的页序重建。
- 不改正文文字、图解尺寸、纸张大小和页面边距。目录中文字体嵌入PDF，不依赖阅读器额外字体。
- 阈值默认30，必要时可在请求体中指定整数toc_min_pages。现有请求体只含title/html也可以。

## 安装

前提：Docker Desktop正在运行，原有Gotenberg的localhost:3000/health正常。本安装命令需要访问镜像、Debian和PyPI下载依赖。新服务使用8084端口，保留已被旧服务占用的8080—8083；启动前请确认8084未被其他程序占用。

在PowerShell进入解压后的文件夹，执行：

```powershell
docker compose -p dify-pdf-navigation up -d --build
Invoke-RestMethod http://localhost:8084/health
```

health应显示status=ok，navigation_version=2026-10-12-v1。如果构建失败，不修改Dify URL，原服务继续可用。重启后容器会自动恢复；Docker Desktop本身仍需启动。

## Dify只改一个渲染URL

若最终PDF HTTP节点使用环境变量PDF_RENDER_URL，把它改为：

```text
http://host.docker.internal:8084/render
```

若节点直接填写URL，就改那个节点的URL。不要改PDF_INSPECT_URL、OCR或其他HTTP节点。

调用仍然是POST，Content-Type: application/json; charset=utf-8，请求体仍选择「请求体生成 → request_body」。响应保留pdf_url、filename，新增page_count和navigation_report；旧下游解析只读取pdf_url/filename即可继续使用。

HTTP读超时应允许原渲染工作完成（建议至少240秒，具体取决于Dify支持的上限）。页码/目录处理无LLM调用；首次构建下载依赖不是一次工作流运行。

## 局部测试

复用上次成功的「请求体生成」缓存输出，仅测试最终PDF HTTP请求，不重跑OCR/改写/图解。如果工作流不能从该节点继续运行，可用PowerShell直接POST保存的request_body JSON文本，随后将响应body放到下游解析节点测试。

42页缓存样例预期：base_page_count=42、toc_enabled=true、toc_pages=2、page_count=44。本包也测试了真实29页和30页的边界：29页无目录，30页插入目录。

如果navigation_report报标题落页无法定位，不能假装目录成功。保留错误详情检查源HTML，不凭正文长度猜页码。最后一页只剩页码等情况由原排版处理，此服务不重新流排正文。

## 回退

只把Dify渲染URL改回原值（通常http://host.docker.internal:8080/render）。8080服务从未被改动。新生成PDF保存在独立Docker数据卷navigation_pdfs中；不要用down -v，否则会删除该服务生成的PDF。

## 验证状态

核心7项测试通过，覆盖29/30页边界、完整正文保全、真实目录偏移、重复标题、长目录与点击目标。与本机Gotenberg真实渲染联测通过；42页缓存插入2页目录，最终44页。部署容器本身尚未在用户Docker中启动，安装后需验证health和一次局部HTTP测试。

此服务只负责导航，不修复上游教材事实、封面主题不匹配或图文数据问题。
